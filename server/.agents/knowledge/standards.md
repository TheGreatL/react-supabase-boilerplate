# Backend Development Standards (Server)

This guide defines the authoritative patterns for the server-side architecture of this boilerplate. All agents working within the `/server` directory MUST follow these rules.

---

## 🏗️ Controller-Service-Repository (CSR)
We enforce a strict separation of concerns:

1. **Controllers (`*.controller.ts`)**
   - Use `asyncHandler` from `shared/utils`.
   - ONLY handle HTTP-related tasks (headers, status codes, response wrapping).
   - Use `ApiResponse` for all successful responses.
   - Never import `db` directly.

2. **Services (`*.service.ts`)**
   - Pure business logic.
   - Maps database models to DTOs.
   - Throws exceptions from `shared/exceptions` — never calls `ApiResponse` directly.
   - Never imports `db` directly — delegates all DB access to the repository.

3. **Repositories (`*.repository.ts`)**
   - The ONLY layer that imports `db` from `shared/database/db`.
   - Uses `Selectable<T>`, `Insertable<T>`, `Updateable<T>` from Kysely.
   - NO business logic — clean queries only.
   - Filters soft-deleted rows with the `active` helper from `shared/lib/db-utils`.

---

## 🛡️ Security & Validation (Triple-Sync Rule)
We enforce the **Triple-Sync Rule**: (1) Zod Schema, (2) Validation Middleware, and (3) Swagger Sync.

- **Zod**: All route inputs MUST be defined in `*.schema.ts`.
- **Validation**: Use `validateSchema(schema, 'type')` for all inputs.
- **CSRF**: `csrfMiddleware` is applied globally — do not disable it.
- **Auth**: Authenticated routes use `authMiddleware`.
- **Dynamic RBAC**: We use modular permissions via the `authorize('MODULE', 'PERMISSION')` middleware.

```ts
// Example: granular permission check
route.delete('/:id', 
  authMiddleware, 
  validateSchema(userByIdParamsSchema, 'params'), 
  authorize('USERS', 'DELETE'), 
  UserController.deleteUser
);
```

---

## 🚨 Exceptions
Always throw from `shared/exceptions` — never write `res.status(...)` in a service.

```ts
// ✅ correct
throw new NotFoundException('User not found');
throw new UnauthorizedException();
throw new ForbiddenException('Admin only');
throw new BadRequestException('Invalid input');
throw new UnprocessableEntityException('Cannot process request');
throw new AlreadyExistException('Email already in use');

// ❌ wrong — never call ApiResponse directly in a service
res.status(404).json({ ... });
```

---

## 📡 API Documentation
- Every endpoint must be registered in the `OpenAPIRegistry` inside its `*.schema.ts` file.
- Documentation and validation MUST be synchronized (Triple-Sync).
- All successful and error responses should be explicitly defined for full schema visibility in Swagger.

---

## 🗄️ Database (Kysely)
- **ORM**: This project uses **Kysely** — not Prisma.
- **Types**: `db.types.ts` is auto-generated by `kysely-codegen`. Never edit it manually.
- **Migrations**: One file per schema change in `src/shared/database/migrations/`. Use `npm run db:make <name>`.
- **Soft Delete**: All models have a `deletedAt` column. Always filter with `.where(active)` when querying.
- **Type helpers**:
  - `Selectable<User>` — rows returned from SELECT
  - `Insertable<User>` — data passed to INSERT
  - `Updateable<User>` — data passed to UPDATE (all fields optional)

---

## 🧪 Testing
- **Unit tests**: Use `vi.hoisted()` + a `class` body inside `vi.mock()` to mock repositories.
- **Assert on message strings**, not `instanceof`, when checking that a service throws — Vitest's isolated module registry causes `instanceof` checks to fail across mock boundaries.
- **Integration tests**: Use `supertest` against the full Express app. No DB required for unit tests.

```ts
// Gold Standard Unit Test Pattern
const repoMethods = vi.hoisted(() => ({
  findById: vi.fn(),
  findAll: vi.fn(),
}));

vi.mock('./user.repository', () => {
  class UserRepository {
    findById = repoMethods.findById;
    findAll = repoMethods.findAll;
  }
  return {UserRepository};
});
```
